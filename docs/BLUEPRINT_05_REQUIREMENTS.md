# AlI Blueprint 0.5 — 通用 2D / 2.5D 可视化游戏开发框架完整升级需求

## 一、项目背景与最终目标

当前项目是基于 Godot 引擎开发的 AlI 插件，已具有游戏蓝图工作台、角色蓝图工作台，以及基础的事件、变量、状态机、输入、动画、音频、场景和游戏流程控制功能。

当前版本为 0.4。

请首先检查项目源码、插件目录、已有蓝图数据、模块手册以及技术文档 `docs/GODOT_BLUEPRINT_TECHNICAL.md`（如果文件存在）。

**注意：这是首次提交本次升级需求。此前并未按照该需求执行开发，不要假定以下功能已经实现。**

本次目标是升级至 AlI Blueprint 0.5。

### 1. 核心定位

参考 Unreal Engine Blueprint 的执行流、数据流和可视化编程机制，以及 Unity NodeCanvas 的状态管理机制，将插件升级为：

**面向 2D 和轻量级 2.5D 游戏的通用可视化开发框架。**

开发者应该能够通过以下工作流程制作游戏：

1. 创建游戏项目或选择基础模板。
2. 导入图片、音频、动画和场景资源。
3. 通过拖拽配置蓝图模块。
4. 在 Godot 场景编辑器中设计地图和 UI。
5. 使用蓝图编排游戏逻辑。
6. 使用串行、并行动画与事件构建交互。
7. 配置输入、相机、音效、设置和存档。
8. 运行并调试游戏。

普通的游戏开发功能应当尽量不需要用户编写 GDScript。

但仍保留自定义脚本扩展能力，不追求完全取消编程。

### 2. 核心设计原则

**通用性**

尽量通过少量通用模块完成多种游戏功能。

例如使用通用属性动画控制按钮、角色、摄像机和场景对象，而不是给每个对象重复制作专用动画模块。

**低操作门槛**

用户能够通过拖入资源、选择参数和连接蓝图完成常见功能。

提供预设，但所有预设应允许修改。

**保留高级自由度**

简单功能通过模块内参数完成，复杂功能仍可以通过执行流、数据流、事件和子图自由组合。

**充分利用 Godot 原生功能**

不要重新实现已经存在的 UI 布局、TileMap 绘制、动画时间轴、资源管理和物理系统。

**兼容现有插件**

尽量保留原有 40 类游戏蓝图模块、10 类角色蓝图模块及已有功能。

允许重构底层，但需要提供旧数据迁移和兼容机制。

**保持模块化**

编辑器、运行时、资源管理、游戏管理器和模板系统应尽可能解耦，便于后续开源和维护。

# 二、统一蓝图编辑器操作体验

## 1. 通用资源拖拽系统

这是第一优先级功能。

所有涉及资源的模块都应支持从 Godot FileSystem 面板直接拖入资源。

支持：

- Texture2D、PNG、JPG、WebP 等图片资源。
- WAV、OGG、MP3 等可导入音频。
- Animation。
- AnimationLibrary。
- SpriteFrames。
- PackedScene。
- TileSet。
- 其他适用的 Godot Resource。

拖入后自动识别资源类型，并填入对应模块参数。

需要支持：

- 拖入资源。
- 点击资源槽选择资源。
- 替换资源。
- 清空资源。
- 显示文件名。
- 图片缩略图。
- 音频试听。
- 动画预览。
- 错误资源提示。
- 资源变更检测。
- 保存和重新加载。

资源关联尽量使用 Godot Resource UID、项目路径及必要的兼容处理，不依赖绝对文件路径。

统一开发可复用的资源槽组件，所有模块共用。

## 2. 折叠式参数面板

蓝图模块应支持可折叠的分类参数区域。

分类标题左侧提供常见的小三角箭头。

点击箭头即可展开或收起。

例如：

Button
- ▼ 基础设置
- ▼ 图片资源
- ▶ 音效
- ▶ 动效
- ▶ 事件

展开后显示具体参数，折叠时尽量保持节点紧凑。

允许显示资源缩略图。

允许预览资源。

尽量记住用户的展开状态。

不要因为参数过多导致节点占据整个蓝图画布。

可根据现有编辑器架构采用节点内部折叠区域，或节点主体配合独立属性检查器的方式。

## 3. 蓝图画布优化

完善：

- 右键搜索创建节点。
- 节点分类。
- 常用节点收藏。
- 多选。
- 复制和粘贴。
- 撤销、重做。
- 端口类型检查。
- 无效连线提示。
- 节点说明。
- 参数提示。
- 节点执行状态显示。
- 运行时错误定位。

执行端口、数据端口和事件端口应明确区分。

保持端口与现有蓝图数据格式兼容。

# 三、通用 UI 系统

## 1. 总体要求

不要把 UI 功能限制在已有的跑酷 HUD 模块中。

新增通用 UI 控制系统。

用户可以在 Godot 场景编辑器中创建普通 Control 节点，然后通过蓝图控制这些节点。

同时支持通过蓝图或场景模板自动创建常见 UI。

优先支持：

- Button。
- TextureButton。
- Label。
- RichTextLabel。
- TextureRect。
- Panel。
- PanelContainer。
- ProgressBar。
- Slider。
- CheckBox。
- LineEdit。
- Control。

通用操作包括：

- 显示、隐藏。
- 设置文字。
- 修改图片。
- 修改 RGBA。
- 修改透明度。
- 设置尺寸。
- 设置位置。
- 修改数值。
- 修改交互状态。
- 读取属性。
- 监听 UI 事件。

尽量复用通用属性读取和写入机制，而不是每种控件制作大量重复模块。

## 2. Button 模块

重点优化 Button。

用户应当能够直接在模块中完成图片、音效和动画配置。

### 图片

支持四种状态：

- Normal。
- Hover。
- Pressed。
- Disabled。

每个状态具有独立的资源拖放区域。

拖入图片后自动显示对应缩略图。

提供按钮状态切换预览。

允许使用默认贴图作为其他状态的回退资源。

### 音效

支持：

- 鼠标悬停音效。
- 按钮点击音效。
- 音量。
- 音频总线。
- 试听。

普通按钮音效直接在模块内配置即可。

不要求额外连接播放声音模块。

### 动效

支持为按钮状态直接绑定常见动画。

例如：

- 鼠标进入：放大到 1.1 倍。
- 鼠标离开：恢复原始大小。
- 鼠标按下：缩小到 0.95 倍。
- 鼠标释放：平滑恢复。
- 点击完成：播放已有动画。

动效底层应复用通用动画控制系统。

### 事件

至少提供：

- Clicked。
- Pressed。
- Released。
- MouseEntered。
- MouseExited。

事件能够连接任意后续蓝图模块。

# 四、通用动画控制系统

## 1. 模块设计

新增通用 Animation 动画控制模块。

目标是通过一个统一模块实现常见属性动画，而不是开发大量独立动效节点。

模块通过下拉菜单选择动画类型。

支持：

1. 放大。
2. 缩小。
3. 位置移动。
4. RGBA 变化。
5. 播放已有动画。

不同类型显示不同参数。

动画可以应用于适用的 Control、Node2D、Sprite2D、Node3D 等对象。

## 2. 放大与缩小

设置：

- 起始缩放。
- 目标缩放。
- 时长。
- 缓动。
- 是否恢复原始大小。

例如：

放大到原始大小的 120%。

缩小到原始大小的 80%。

放大和缩小共用底层插值逻辑。

## 3. 位置动画

设置：

- 目标位置。
- 相对位移或绝对坐标。
- 动画时长。
- 缓动方式。

支持 Vector2 和 Vector3。

根据目标节点类型自动选择。

适用于 UI 移动、物体移动、镜头移动、场景演出等。

## 4. RGBA 动画

支持：

- R。
- G。
- B。
- Alpha。

允许配置起始颜色、目标颜色和过渡时长。

用于：

- UI 淡入淡出。
- 角色闪红。
- 图像颜色变化。
- 场景物体渐隐。
- 提示信息显示与消失。

## 5. 通用参数

提供：

- 目标节点。
- 动画持续时间。
- 延迟。
- Ease。
- Transition。
- 循环。
- 是否反向。
- 是否恢复初始状态。
- 是否等待动画结束。
- 播放完成事件。
- 取消事件。
- 失败事件。

底层优先使用 Godot Tween。

同一属性被多个动画同时修改时，需要明确覆盖、取消或排队策略。

避免重复点击造成动画状态混乱。

## 6. 预览

动画模块提供预览按钮。

用户可以：

- 播放预览。
- 停止预览。
- 重播。
- 修改参数。
- 查看最终效果。

预览不能永久修改原始场景状态。

结束预览后应恢复初始属性。

对于受到 Container 布局约束的 UI，应采用合适的包装节点或其他方案，避免位置和缩放被自动布局覆盖。

# 五、动画资源拖拽与自动配置

## 1. 直接使用已有动画

用户可以将 Animation 资源直接拖入动画控制模块。

插件应尽可能自动完成 AnimationPlayer 的配置。

具体包括：

1. 识别 Animation 资源。
2. 获取目标节点。
3. 检查是否已有可用 AnimationPlayer。
4. 优先复用已有节点。
5. 如果不存在，允许自动创建。
6. 创建或关联 AnimationLibrary。
7. 添加动画。
8. 配置播放名称。
9. 配置播放接口。
10. 提供预览。

必须检查动画轨道引用的节点路径是否有效。

如果动画资源来自不同场景，提供目标路径重映射或手动绑定方式。

不允许静默修改其他场景共享的动画资源。

## 2. 直接拖入 AnimationPlayer

允许从场景树拖入已有 AnimationPlayer。

自动读取动画列表。

用户选择动画名称即可使用。

支持：

- 播放。
- 停止。
- 暂停。
- 恢复。
- 反向。
- 速度。
- 循环配置。
- 动画完成事件。

## 3. SpriteFrames 与图片序列

支持直接拖入 SpriteFrames。

自动绑定适用的 AnimatedSprite2D 或 AnimatedSprite3D。

允许选择具体动画。

同时提供图片序列导入向导：

- 多张连续图片。
- Sprite Sheet。
- 行列切割。
- 帧率。
- 循环。
- 帧顺序。

默认使用 SpriteFrames。

用户明确选择 AnimationPlayer 时，才生成相应动画轨道。

不要把普通单张 PNG 误判为完整动画。

## 4. 统一动画接口

已有角色蓝图、场景节点播放动画和新 Animation 模块应共享必要的播放接口。

不要形成几套互不兼容的动画管理系统。

# 六、通用串行与并行执行系统

这是整个蓝图系统的重要底层能力。

## 1. 执行模型

目前已有 Sequence 模块仅负责按顺序触发执行出口。

本次需要增加真正支持等待的异步执行模型。

保留原有 Sequence 语义，不要直接修改造成旧蓝图行为变化。

新增可等待的串行与并行编排模块。

## 2. 串行执行

支持：

动画 A → 等待 A 完成 → 动画 B → 等待 B 完成 → 下一事件。

需要依靠实际完成信号，而不是单纯触发执行端口。

串行执行应支持：

- 属性动画。
- AnimationPlayer 动画。
- 延迟。
- 场景转场。
- 可等待子图。
- 其他异步操作。

## 3. 并行执行

允许多个操作同时启动。

例如：

- 放大。
- 向上移动。
- Alpha 渐变。

这些动画可以同时作用于同一个对象的不同属性。

默认等待所有分支完成后继续。

也允许设置立即继续，不等待结果。

## 4. 嵌套编排

支持：

- 串行组包含并行组。
- 并行组包含串行分支。
- 多个动画组合成可复用子图。

例如：

按钮点击
→ 并行播放缩放和音效
→ 等待动画完成
→ 播放界面淡出
→ 等待淡出完成
→ 切换场景。

## 5. 任务生命周期

需要处理：

- 正常完成。
- 主动取消。
- 中途失败。
- 节点被删除。
- 场景切换。
- 重复触发。
- 无限循环动画。
- 游戏暂停。
- 多分支等待。

建议建立统一的运行任务状态与取消机制。

避免异步流程永久等待。

避免重复触发完成事件。

# 七、相机控制系统

## 1. 通用 Camera Controller

新增通用 Camera Controller 蓝图模块。

根据目标相机类型，显示对应参数。

支持从场景树拖入 Camera2D 或 Camera3D。

自动识别类型。

## 2. Camera2D

支持：

- 相机位置。
- 平滑移动。
- 目标跟随。
- 缩放。
- 平面旋转。
- 镜头震动。
- 相机切换。
- 视角偏移。
- 平滑过渡。
- 指定边界和常用限制。

所有相机运动尽量复用通用动画执行系统。

## 3. Camera3D

支持：

- 相机位置。
- 三维旋转。
- Yaw、Pitch、Roll。
- 围绕目标旋转。
- 看向指定节点。
- 跟随目标。
- 透视投影。
- 正交投影。
- FOV。
- 正交视野尺寸。
- 镜头震动。
- 相机切换。
- 平滑过渡。

支持指定 Pivot 节点作为旋转中心。

允许直接输入角度，也允许使用预设视角。

## 4. 相机预设

提供：

- 正面。
- 侧面。
- 俯视。
- 斜45度。
- 等距视角。
- 自定义视角。

预设参数应允许修改。

支持两个相机位置或观察角度之间的平滑切换。

## 5. 与串并行系统整合

例如：

点击切换视角按钮
→ Camera3D 旋转90度
→ UI 箭头同时淡出
→ 等待两者完成
→ 更新可交互对象
→ 播放提示音效。

相机操作必须具有完成、取消和失败输出。

## 6. 编辑器预览

允许在编辑器中预览相机视角和过渡效果。

预览不能永久修改场景。

# 八、2.5D 游戏支持

## 1. 总体定位

在保留纯 2D 开发能力的基础上，为类似《饥荒》的 2.5D 游戏提供基础支持。

不要求全面实现复杂 3D 游戏开发功能。

重点支持：

**3D 空间 + 2D 美术资源 + Camera3D。**

## 2. 场景结构

支持以下基本对象：

- Node3D。
- Camera3D。
- MeshInstance3D。
- Sprite3D。
- AnimatedSprite3D。
- 必要的碰撞节点。

允许使用二维图片作为三维空间中的精灵平面。

## 3. Billboard 模式

支持：

- 精灵始终朝向相机。
- 仅围绕指定轴朝向相机。
- 固定方向。
- 根据方向切换动画。

允许用户拖入二维角色图片或 SpriteFrames，并配置为适用的 3D 精灵资源。

不应要求用户必须制作完整的 3D 人物模型。

## 4. 基础 2.5D 场景模板

提供一个简单的 2.5D 模板。

包括：

- 三维地面。
- 倾斜 Camera3D。
- Sprite3D 或 AnimatedSprite3D 示例。
- 基础移动与碰撞接口。
- 相机角度配置。
- 简单场景对象。

能够直接运行并作为新项目基础。

## 5. 2D 与 3D 的边界

必须明确：

普通 Camera2D 不能生成真实三维透视。

单张二维背景不会因为旋转相机而自动产生真实侧面、背面或遮挡关系。

纯 2D 场景继续使用 Node2D、Camera2D。

2.5D 场景使用 Node3D、Camera3D，并结合二维美术资源。

必要时支持 SubViewport 混合显示。

蓝图底层应尽量共享逻辑执行、事件、变量、动画和状态管理。

# 九、背景、地图与 TileMap 系统

## 1. 通用背景管理

新增 Background 模块。

支持：

- 拖入图片创建背景。
- 自动创建或绑定 Sprite2D。
- 设置位置。
- 设置尺寸与缩放。
- 设置旋转。
- 设置透明度。
- 设置层级。
- 图片平铺与重复。
- 多层背景。
- Parallax2D 视差滚动。
- 背景切换。
- 背景动画。

背景动画复用通用动画模块。

## 2. TileMap 系统

使用当前项目 Godot 版本支持的正式地图接口。

对于支持 TileMapLayer 的 Godot 4 版本，优先采用 TileMapLayer 与 TileSet。

不要基于旧版 TileMap API 重新开发系统。

支持：

- 拖入 TileSet。
- 从场景树绑定 TileMapLayer。
- 自动创建 TileMapLayer。
- 显示瓦片资源。
- 选择瓦片。
- 设置图层。
- 放置瓦片。
- 删除瓦片。
- 替换瓦片。
- 填充区域。
- 清空区域。
- 读取格子数据。
- 世界坐标和格子坐标转换。
- 使用 TileSet 已配置的地形自动连接。

支持多个 TileMapLayer，例如：

- 地面。
- 墙壁。
- 装饰。
- 前景。
- 遮挡。

需要注意图层显示顺序。

## 3. TileSet 导入

# 二十、最终目标与验收标准
