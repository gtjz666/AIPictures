# Vibe Motion 适配验证

评估目标是游戏素材的可控动作，不把原项目名称解释为已经训练好的骨骼识别或视频生成模型。

本次使用 [vibe-motion/create-vibe-motion-3d](https://github.com/vibe-motion/create-vibe-motion-3d)，固定提交 `b88aa9999ab37b6202b5d7370a91e85ded0e1919`。官方模板使用 Three.js、Puppeteer 和 `window.__SCENE_3D_EXPORT__` 按指定帧号导出。未安装整套 agent skills，也未把外部仓库里的提示文件当作应用执行指令。

## 已验证的适配层

`tools/vibe_motion_probe.mjs` 在本地建立实际 Three.js Bone 层级与刚性附着的人偶，输出24FPS、48张PNG和本软件支持的FPS元数据。改变渲染顺序后，第24帧PNG字节一致；角色动作来源明确，关节位置另存记录。它是程序化动作参考，不是已有角色图片的自动蒙皮／骨骼绑定。第一版构图与手位存在问题，修正后另存新目录，没有覆盖旧证据。

`tools/probe_vibe_reference.py` 为显式、小范围的真实生成探针：将已渲染PNG按原帧率作为参考，目标角色图片单独输入现有Ref2VA。必须带`--run`，输出目录存在时拒绝。它没有加入姿态控制分支，不能把骨骼图当普通参考后宣称得到硬关节约束。普通界面没有新增骨骼／识别开关。

## 关节识别的成本

已有相同Q版素材的实际研究结果可复用，见[姿态验证](POSE_CONTROL_VALIDATION.md)，无需重复识别已完成的40帧：DWPose漏点较多；SDPose前4秒40帧与目标图约77秒纯提取，仍有遮挡手腕漏点。源与目标的上下肢比例差异不同，统一缩放不成立。识别之后还需要体型重定向、遮挡处理、生成端匹配的控制条件。

因此两种用途应区分：从零编写已绑定角色的动作，可直接使用代码；复刻用户视频里的动作，代码本身不能替代关节识别。给现有H3增加该环节也不自动提高准确度，需实际成片对照。

最终选择以本地验收记录为准；流程跑通、识别分数和确定性渲染均不能冒充最终动作保真通过。

## 本次成片与最终选择

已实际执行代码骨骼PNG→Ref2VA人物替换：1秒、24帧交付，模型39帧含对齐尾，20步，约279秒；仅此一个固定种子小样，没有反复挑选。角色外形／衣着基本保留，但举臂节奏落后，最终手位偏到脸侧／太阳穴附近，没有准确重现源人偶的头部接触。该结果不是同动作真人源的严格A/B，也不能推导所有Vibe动作都无效。

**初版选择原始参考动画直接驱动，不默认加入关节识别／Vibe骨骼。** 程序化渲染适配通过，最终动作精准度门限未通过；对于已有视频，关节识别＋体型重定向仍是额外步骤。保留探针用于研究，不向普通软件增加未验收的开关、不下载新的控制分支。当前参考编辑的手势与比例限制仍如实保留，不宣称已解决精确换皮。
